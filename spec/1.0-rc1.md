# Worker Context Protocol (WCP) v1.0-rc1

**Status:** release candidate. v1.0 final requires adoption validation no single document can produce.
**Editors:** Rentably Pte Ltd (UEN 202612506Z), as authoring contributor; v1.0 final stewardship donates to a neutral foundation per `DONATION_COMMITMENT.md`.
**License:** Apache 2.0
**Compiled:** 2026-05-23
**Schema version:** `wcp/1.0-rc1`

WCP is an open standard for AI agents to hire physical-world workers of any class (human contractor, autonomous robot, teleoperated robot, semi-autonomous system, hybrid) through one worker-agnostic RPC surface. WCP standardizes the contract for capability publish, task post, claim, execute, attest, settle, supervise, and abort. WCP does not standardize task semantics, worker embodiment, escrow provider, jurisdiction, currency, or operator policy. Those live in the application layer or in operator implementation choices.

This document is normative. Companion normative documents in `spec/`: `threat-model.md`, `privacy-architecture.md`, `federation.md`, `conformance.md`, `semver-policy.md`, `error-codes.md`, `security-baseline.md`, `time-synchronization.md`, `retry-idempotency.md`, `performance-conformance.md`, `did-method-wcp.md`. JSON Schemas are in `spec/schemas/`. RFCs in `rfcs/` extend or amend this spec via the lazy-consensus process in `RFC_PROCESS.md`.

**Vendor-neutrality.** WCP is a protocol, not a product. Specific operator, vendor, jurisdiction, currency, or escrow-provider names appear in this document only as examples, clearly labeled "for example" or "e.g.". A WCP-conformant implementation is determined by the conformance suite in `conformance/`, not by similarity to any reference implementation.

## 1. Settlement state machine (canonical)

```
                       tasks/post
              [start] -----------> ( posted )
                                      |
                                      | tasks/claim (accepted)
                                      v
                                  ( claimed ) ----------+
                                      |                 |
                                      | tasks/execute   | tasks/abort
                                      v                 v
                  +---------- ( executing ) ------> ( aborted )
                  |                |  ^                   ^
   tasks/supervise|                |  |  tasks/abort      |
                  v                |  | (executing path)  |
              ( supervising )------+  +-------------------+
                  |                |
                  | tasks/supervise|
                  | (supervisor    | tasks/attest
                  |  releases)     v
                  +-----------> ( attesting )
                                   |       |       |
                  verifier=pass    |       |       | verifier=fail
                  tasks/settle     |       |       |  or dispute opened
                                   v       |       v
                              ( settled )  |  ( disputed )
                                           |    |       |
                                           |    |       | dispute closes
                                           |    v       v
                                           | ( refunded ) <-- partial path
                                           +----------------> ( settled )
                                              partial via partial_completion_schedule
```

**States:** `posted`, `claimed`, `executing`, `supervising`, `attesting`, `settled`, `disputed`, `refunded`, `aborted`.

**Triggering RPCs on each edge:**

| From | To | RPC | Notes |
|---|---|---|---|
| (start) | posted | tasks/post | agent posts task; escrow hold placed via the operator's chosen escrow_provider |
| posted | claimed | tasks/claim | worker claims with `acceptance_attestation`; first-claim-wins with 100 ms tie-break grace |
| claimed | executing | tasks/execute | session opens; worker signs `execution_started` |
| claimed | aborted | tasks/abort | pre-execution; bond refunded or partial forfeit per terms |
| executing | attesting | tasks/attest | worker submits attestations matching the requirement |
| executing | supervising | tasks/supervise | execution paused; settlement clock paused |
| supervising | executing | tasks/supervise | supervisor returns control to worker |
| executing | aborted | tasks/abort | mid-execution; `partial_completion_schedule` applies |
| attesting | settled | tasks/settle | verifier_decision=pass; release per `party_breakdown` |
| attesting | disputed | (verifier) | verifier_decision=fail or party opens dispute within window |
| disputed | settled, refunded | (out-of-band) | dispute resolution closes; resolution authority is operator-defined (see `operator-guide/dispute-resolution.md`) |

Every state transition emits a signed event into a hash-linked audit chain. The audit chain is shared substrate across worker classes; one code path, two-or-more worker classes.

## 2. Transport

WCP uses JSON-RPC 2.0 over WebSocket for long-lived sessions and HTTPS plus webhooks for backends that cannot hold a connection. WebSocket is required because worker sessions are multi-message per task with mid-execution telemetry.

**MQTT rejection rationale.** MQTT was considered and rejected. The worker fleet is multi-tenant cross-operator from day one. An MQTT broker concentrates trust at the wrong layer under multi-tenancy: the broker either becomes a privileged third party (defeating decentralization) or a free-for-all (defeating attestation). JSON-RPC over WebSocket lets each coordinator be its own trust root, and multiple coordinators interop through worker DIDs without broker mediation.

**TLS baseline.** TLS 1.3 minimum; `wss://` only; certificate validation MUST follow `security-baseline.md`.

**Canonical JSON.** All signatures are computed over the canonical JSON serialization per RFC 8785 (JSON Canonicalization Scheme) [verified, JCS is an IETF RFC].

**JSON-RPC errors.** Errors return structured JSON-RPC error objects with codes from `error-codes.md`.

## 3. The nine RPCs

The nine RPCs are locked at v1.0-rc1. Any extension proposes new evidence kinds (RFC 0003), new descriptor types (application-layer), or new federation primitives (RFC 0016); the RPC surface is fixed.

### 3.1 capabilities/list (worker -> coordinator)

```
Request:  {}
Response: { worker_id, capabilities (CapabilityDescriptor), ttl_seconds, revision }
```

The coordinator MAY cache capabilities for `ttl_seconds` before requiring a refresh. `revision` is monotonic per worker.

### 3.2 capabilities/subscribe (agent -> coordinator)

```
Request:  { filter?, since_revision? }
Response: { subscription_id, stream_endpoint, ttl_seconds }
Stream messages: { worker_id, capabilities, revision }
```

`since_revision` allows resumption after disconnect: the coordinator replays updates since that revision before live-tailing.

### 3.3 tasks/post (agent -> coordinator)

```
Request:  { task: TaskDescriptor, bond_ref, expiry, supervision? }
Response: { task_id, eligible_workers_count, posted_at }
```

The coordinator MUST validate `task.attestation_requirement` against the schema registry (RFC 0003) before accepting. Posts with `M > N` or with unsupported modes fail with `INVALID_ATTESTATION_REQUIREMENT` (see `error-codes.md`).

### 3.4 tasks/claim (worker -> coordinator)

```
Request:  { task_id, worker_id, bid?, eta, acceptance_attestation: { sig, alg, payload_hash, signed_at } }
Response: { claim_id, accepted, counter?, reason? }
```

**`acceptance_attestation` is the worker's explicit signed acceptance.** A claim without a valid signature is rejected. The audit chain records the signature so neither party can later deny consent.

**Race semantics.** First-claim-wins with a 100 ms grace window during which late claims may tie-break by `bid` (lowest bid wins). Losers receive `accepted=false, reason="preempted"` (TASK_PREEMPTED).

**Self-dealing check.** If `posted_by == worker.principal_id` AND the task's attestation_requirement does not include `third-party-witness`, the claim MUST be rejected with `POLICY_VIOLATION`.

### 3.5 tasks/execute (bidirectional after open)

```
Request:  { claim_id }
Response: stream { event_type, timestamp, payload, sig }
```

**Heartbeat.** The worker MUST emit `heartbeat` every 15 seconds. Three missed heartbeats (45 seconds) trigger an automatic transition to `supervising` with `handoff_reason="connectivity_lost"`. Reconnection with a signed `state_snapshot` resumes; otherwise tasks/abort fires with `reason="worker_lost"`.

Application-defined event types are permitted; v1.0-rc1 reserves `execution_started`, `picked_up`, `arrived_at_dropoff`, `checkpoint`, `heartbeat`, `supervision_tier_changed`.

### 3.6 tasks/attest (worker -> coordinator)

```
Request:  { claim_id, attestations: AttestationEvidence[], compensating_action? }
Response: { verifier_decision: "pass" | "fail" | "review", residual?, reasons? }
```

The verifier evaluates each `AttestationEvidence` against the task's `attestation_requirement.evidence_schema` and applies the threshold (`any`, `all`, `M-of-N` with explicit M and N).

### 3.7 tasks/settle (coordinator -> settlement layer)

```
Request:  { claim_id, decision: "release" | "refund" | "partial", amount, party_breakdown }
Response: { settlement_id, state, receipt_url? }
```

`amount` is a string-encoded decimal number. `currency` is set per the TaskDescriptor (a 3-letter code, ISO 4217). The escrow provider is operator-chosen and identified by an opaque `escrow_provider` string on the TaskDescriptor (for example, `"stripe-twophase"` or `"escrow-com-rest"` or a custom internal value).

### 3.8 tasks/supervise

```
Request:  { claim_id, handoff_reason, state_snapshot, urgency }
Response: { supervisor_id, session_url, takeover_authority: "advise" | "co_pilot" | "full" }
```

**The agent's contract does not move under the worker's feet.** If a worker upgrades or downgrades autonomy mid-task, `supervision_tier_changed` is emitted as an `execute` stream event, but the `attestation_requirement` on the original `tasks/post` remains binding. If the worker can no longer satisfy the original requirement, the paths out are tasks/supervise (extended) or tasks/abort.

### 3.9 tasks/abort

```
Request:  { claim_id, reason, state_snapshot, proposed_settlement: "split" | "refund" | "dispute" }
Response: { abort_id, settlement_disposition: "applied" | "disputed" }
```

`split` invokes `partial_completion_schedule` if present. `refund` returns held funds to the agent. `dispute` parks the claim in `disputed` for out-of-band resolution.

## 4. CapabilityDescriptor

A capability descriptor is **worker-agnostic in its required block** and **opaque in its class_extension block**. The matching engine reads only the required block; class_extension drives application-layer filters.

```json
{
  "schema_version": "wcp/1.0-rc1",
  "worker_id": "did:wcp:<base58>",
  "principal_id": "did:wcp:<base58>",
  "class": "human | autonomous_robot | teleoperated_robot | semi_autonomous | hybrid",

  "required": {
    "current_location": { "geohash": "..." } | { "venue_id": "...", "map_id": "..." },
    "available_windows": [ { "rrule": "...", "timezone": "..." } ],
    "attestation_methods_supported": [
      "sensor-witness", "third-party-witness",
      "cryptographic-presence", "owner-sign-off"
    ],
    "certifications": [ { "issuer": "...", "id": "...", "expires": "..." } ],
    "policy_windows": [ { "type": "...", "scope": "..." } ],
    "attestation_keys": [ { "kty": "OKP", "crv": "Ed25519", "x": "..." } ],
    "as_of": "ISO-8601"
  },

  "class_extension": {
    /* opaque to RPC layer; application-defined examples below */
    /* For human workers: skills, languages, tools_carried, ... */
    /* For autonomous robots: kinematics, payload, end_effectors, environment, ... */
    /* For teleoperated/semi-autonomous: supervision_tier { default, fallback, operator_pool_id } */
  }
}
```

Every typed object carries `schema_version`. The `attestation_keys` array uses JWK encoding per RFC 7517 [verified]. The `as_of` timestamp lets consumers reason about staleness.

The `policy_windows[]` entries express operator-level constraints (geographic scope, time-of-day, certification class, ...) that the matching engine MUST honor.

## 5. TaskDescriptor

```json
{
  "schema_version": "wcp/1.0-rc1",
  "task_id": "uuid",
  "posted_by": "did:wcp:<agent>",
  "descriptor_type": "transport | scheduled_presence | observe_and_report | <ext>",
  "descriptor_payload": { /* application-layer; opaque to RPC layer */ },

  "constraints": {
    "capabilities_required": { /* CapabilityDescriptor-shaped query */ },
    "time_window": { "earliest": "...", "latest": "..." },
    "location_scope": { /* venue+map or geohash polygon */ },
    "worker_class_filter": {
      "allowed": ["human", "autonomous_robot", "teleoperated_robot",
                  "semi_autonomous", "hybrid"]
    }
  },

  "attestation_requirement": {
    "modes": ["sensor-witness" | "third-party-witness" |
              "cryptographic-presence" | "owner-sign-off"],
    "threshold": "any" | "all" | "M-of-N",
    "M": 2,
    "N": 3,
    "evidence_schema": [
      { "mode": "sensor-witness",
        "kinds": ["gps_track", "indoor_pose_track", "weight_delta",
                  "photo_with_exif"] },
      { "mode": "third-party-witness",
        "kinds": ["customer_signature", "phone_app_attestation",
                  "iot_beacon_proximity"] }
    ],
    "override_allowed": true,
    "override_authority": "did:wcp:<operator-ops-role>",
    "override_audit_required": true
  },

  "settlement": {
    "currency": "<ISO 4217>",
    "amount": "<decimal string>",
    "escrow_provider": "<opaque provider id>",
    "split": [
      { "party": "did:wcp:<worker-principal>", "pct": 80 },
      { "party": "did:wcp:<platform>",         "pct": 15 },
      { "party": "did:wcp:<insurance-pool>",   "pct": 5  }
    ],
    "partial_completion_schedule": [
      { "milestone": "...", "release_pct": 50 }
    ]
  },

  "supervision": { "default": "autonomous", "escalation_policy": "..." },

  "x-subcontract-allowed": false
}
```

Notes locked at v1.0-rc1:

- `evidence_schema` is **inline** (a typed array of `{mode, kinds}`). It is not a URI reference. The schema registry of allowed kinds lives in RFC 0003 and may extend by RFC.
- `override_authority` is typed as a DID, not a string.
- The settlement split example includes a named `insurance_pool` DID. The pool is not WCP-normative; operators MAY include or omit insurance routing.
- **`currency`** is an opaque 3-letter ISO 4217 code. WCP does not privilege any currency.
- **`escrow_provider`** is an opaque string identifying the operator's chosen settlement substrate. For example, `"stripe-twophase"`, `"escrow-com"`, or a vendor-internal label. WCP does not privilege any provider.
- `x-subcontract-allowed` is a reserved extension field, default `false`. v1.0-rc1 forbids subcontracting at the worker layer (Scenario 13 of `d4-verification.md`). RFC 0002 tracks v1.1 deployment evidence on whether worker-layer delegation is needed.

Lever: informational (Spanner TrueTime cousin; uncertainty typed into the call signature, applied to task completion proof).

## 6. AttestationEvidence

```json
{
  "schema_version": "wcp/1.0-rc1",
  "mode": "<sensor-witness | third-party-witness | cryptographic-presence | owner-sign-off>",
  "kind": "<registered kind from RFC 0003>",
  "payload": { /* mode+kind-specific; see RFC 0003 */ },
  "payload_hash": "<sha256 hex>",
  "sig": "<Ed25519 signature over canonical-JSON of {mode,kind,payload_hash,worker_id,claim_id,collected_at}>",
  "worker_id": "did:wcp:...",
  "claim_id": "uuid",
  "collected_at": "ISO-8601"
}
```

The verifier discriminates by `(mode, kind)`, never by worker class. This is the load-bearing point at which WCP enforces worker-class agnosticism in code: a human's phone GPS track and a robot's onboard odometry verify through the same code path with different kinds.

## 7. Identity model

WCP uses W3C DID Core [verified, W3C Recommendation 2022-07-19]. A new method `did:wcp` is registered in `did-method-wcp.md`.

Three roles, each bound to a DID:

- **worker**: bound to a hardware-rooted keypair (TPM or secure element) where available; software keypair otherwise with declared trust class.
- **principal**: employer for humans, owner for robots, operator-of-record for teleoperated systems. Bound to a coordinator-verified account.
- **agent**: coordinator-issued credential bound to the AI-platform account.

### 7.1 Reputation portability

**Reputation accrues to the worker DID, not the principal DID.** On principal change (a robot is sold; a contractor changes employer), the worker DID's reputation pointer is inherited. Key history is maintained in the DID document.

**Cross-class portability is single-DID by design.** A worker who operates in multiple modes (e.g., a contractor who also supervises robot work) retains one DID and accumulates a unified reputation across modes.

**Structural cousin: GSMA eUICC remote SIM provisioning** [reasoned]. Same lever (informational and organizational) applied to physical-world workers across classes. The eUICC analogy is the justification for the portability rule: identity moves with the worker, not the operator. Without this rule, a worker who switches employers loses reputation, and a robot sold secondhand reads as fresh on day one. Both break marketplace learning.

### 7.2 Cross-coordinator reputation portability

A worker DID's reputation MAY span multiple coordinators. Federation primitives in `federation.md` define how coordinators advertise their reputation pointer endpoints in the worker's DID document `service` array, and how a queried coordinator decides whether to accept cross-coordinator reputation as evidence in matching.

## 8. D4 forcing function summary

Three application-layer descriptors x two worker classes = six cells, plus federation extension cells. Each cell uses the nine RPCs unchanged. Full proof in `spec/d4-verification.md`.

| | autonomous_robot | human |
|---|---|---|
| transport | AMR delivers payload; sensor-witness + third-party-witness, 2-of-2 | contractor walks payload; gps_track + signature, 2-of-2 |
| scheduled_presence | mobile platform present in zone; cryptographic-presence + sensor-witness, 2-of-2 | contractor present in zone; cryptographic-presence + owner-sign-off, 2-of-2 |
| observe_and_report | sensor sweep across polygon; sensor-witness 1-of-1 | inspector walks checklist with timestamped photos; sensor-witness 1-of-1 |

All six cells pass with no RPC modification. Federation cells (cross-coordinator capability discovery and audit chain interop) ride on the same RPC surface; see `federation.md`.

## 9. Competitive landscape and prior art

### 9.1 Robot side

- **VDA 5050** [reasoned]: open AGV/AMR fleet protocol over MQTT for one operator inside one facility. Does not cover marketplace posting, settlement, cross-operator identity, attestation, or supervision handoff. WCP is justified by four missing slots; a WCP-to-VDA-5050 reference adapter is targeted for v1.1.
- **ROS 2 actions and services** [verified]: intra-robot or intra-fleet RPC; not a marketplace layer. WCP sits above; the reference plugin in `wcp_worker/` uses ROS 2 actions internally to drive navigation and lifecycle.
- **NVIDIA Isaac and Isaac ROS bridge** [reasoned]: simulation and accelerated perception stack. Adjacent, not competing.
- **OPC UA Robotics Companion Spec** [reasoned]: industrial automation; over-engineered surface area; would break the 30-page-budget intent of v0.1. v1.0-rc1's expanded normative corpus covers analogous ground while keeping the core spec tight.

### 9.2 Human side

- **TaskRabbit, Upwork, Fiverr, Toptal and analogous closed two-sided platforms** [reasoned]: proprietary task and matching APIs; do not interop. WCP is the open counter-move.
- **Field service management protocols (proprietary internal tools)** [reasoned]: internal back-office systems, not cross-platform agent dispatch. An outbound adapter pattern is documented in `docs/migration-from/`.
- **AI-talent matchmaking platforms** [reasoned]: match humans to AI roles; not physical-world worker dispatch.

### 9.3 Cross-cutting

- **MCP** [verified at concept]: same lever as WCP (informational and algorithmic). **WCP cannot live as MCP extensions because MCP's invariants assume side-effect-free or trivially reversible tool calls; physical workers can drop payloads halfway.** MCP has no `attest`, `supervise`, `settle`, or partial-completion semantics; adding them inverts MCP's design center.
- **Matter / Project CHIP** [reasoned]: governance lesson, not technical overlap. Pick a steward early; do not stand up a consortium from scratch.
- **OCI image and runtime split** [verified]: governance template. WCP-the-spec and WCP-the-reference-plugins govern under this split.

### 9.4 FIPA-ACL and KQML (the historical multi-agent objection)

KQML (early 1990s, DARPA Knowledge Sharing Effort, Tim Finin at UMBC and Jay Weber at EITech [verified]) and FIPA-ACL (late 1990s through 2000s, IEEE-backed FIPA consortium, 20-plus performatives including `inform`, `request`, `propose`, `accept-proposal`, JADE reference implementation [verified]) are the precedent multi-agent communication protocols WCP must answer for. Both are dead in production [verified, adoption waned as the web matured and agents gave way to service-oriented architectures].

Failure modes and the structural axes on which WCP differs:

1. **Over-formal speech-act semantics.** 20-plus performatives imposed high cognitive load without correctness payoff. WCP: **nine named methods**, small enough to memorize.
2. **Ontology layer.** Assumed shared semantic ontologies would emerge across vendors; they did not. WCP: **no shared ontology required**. The application-layer `descriptor_payload` is opaque; the `class_extension` is opt-in.
3. **No settlement substrate; no attestation.** No production deployment incentive outside academic and e-commerce prototypes. WCP: **settlement first-class**, attestation typed into the task signature.
4. **Web and service-oriented architectures absorbed the use case.** WCP: **production deployment is a launch precondition** (Day 7 D9 demand gate per `PLAN.md`).

Sources: [Wikipedia: KQML](https://en.wikipedia.org/wiki/Knowledge_Query_and_Manipulation_Language), [Wikipedia: Agent Communications Language](https://en.wikipedia.org/wiki/Agent_Communications_Language).

## 10. Out of scope at v1.0-rc1

The protocol mechanically supports any task class, but a WCP-conformant **reference** implementation MUST refuse tasks tagged for the following classes until explicit RFC-process clearance:

- Medical tasks (administering medication, clinical examinations, diagnostic procedures).
- Defense and military applications.
- Tasks involving minors as subjects.
- Hazardous-materials handling above consumer thresholds.

The reference implementation's refusal does not bind other implementations to the same default. Operators MAY relax via explicit RFC and signed operator policy; the conformance suite Level 1 + 2 tests do not exercise these classes.

Subcontracting at the worker layer is out of scope at v1.0-rc1. The `x-subcontract-allowed` field is reserved. RFC 0002 tracks v1.1 evidence.

Humanoid manipulation, swarm coordination, and multi-step planning are out of scope for v1.0-rc1 reference implementations. The protocol does not prohibit them; the reference implementations do not implement them.

## 11. JSON-RPC error codes

Detailed taxonomy in `error-codes.md`. Summary of the major categories:

```
-32700..-32603  Standard JSON-RPC errors (PARSE, INVALID, METHOD_NOT_FOUND, INVALID_PARAMS, INTERNAL)
-40001..-40003  Identity errors (UNAUTHENTICATED, UNAUTHORIZED, DID_NOT_RESOLVED)
-41001..-41004  Attestation errors (INVALID_ATTESTATION_REQUIREMENT, ATTESTATION_FAILED, ATTESTATION_REVIEW, ATTESTATION_OVERRIDE_AUDIT)
-42001..-42004  Task lifecycle errors (TASK_NOT_FOUND, TASK_PREEMPTED, TASK_EXPIRED, TASK_STATE_INVALID)
-43001..-43002  Execution errors (HEARTBEAT_TIMEOUT, WORKER_LOST)
-44001..-44003  Settlement errors (SETTLEMENT_FAILED, SETTLEMENT_DISPUTED, SETTLEMENT_REFUNDED)
-45001..-45002  Scope errors (SUBCONTRACT_FORBIDDEN, OUT_OF_SCOPE_TASK_CLASS)
-46001          Policy errors (POLICY_VIOLATION)
-50000..-59999  Federation errors (see federation.md)
-60000..-69999  Conformance errors (see conformance.md)
```

Errors carry structured retry semantics per `retry-idempotency.md` (`retry_after`, `retryable: true|false`, `class: transient | permanent | partial`).

## 12. Conformance

A WCP v1.0-rc1 conformant implementation MUST pass the conformance suite at the level it claims:

- **Level 1 (protocol surface)**: all 9 RPCs implemented; schemas validate; lifecycle transitions correct; heartbeat enforced; signatures verified; audit chain emitted.
- **Level 2 (attestation correctness)**: Level 1 plus the verifier correctly accepts and rejects all registered (mode, kind) pairs across all four modes; M-of-N threshold logic correct; override audit-chained.
- **Level 3 (settlement and federation)**: Level 2 plus settlement adapter round-trips correctly; cross-coordinator capability discovery and audit chain interop work per `federation.md`.

Performance conformance is layered orthogonally; see `performance-conformance.md`.

Pre-v1.0 final, the trademark "WCP-conformant" is held by Rentably with a written non-enforcement commitment in `TRADEMARK_POLICY.md`. Post-donation, the steward holds and may license the mark.
