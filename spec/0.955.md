# Worker Context Protocol (WCP) v0.955

**Status:** normative, supersedes `spec/0.2.md` for the sections this document covers.
**Editors:** Rentably Pte Ltd (UEN 202612506Z), as authoring contributor; v1.0 final stewardship donates to a neutral foundation per `DONATION_COMMITMENT.md`.
**License:** Apache 2.0
**Compiled:** 2026-05-23
**Schema version:** `wcp/0.2` (wire identifier unchanged; the breaking change is a contraction of the surface that callers send and receive, not a rename of the protocol envelope).

This document is the normative spec layer for v0.955. It is a breaking-change update to the surface previously documented in `spec/0.2.md`. Where the two documents disagree about RPC count, state machine, descriptor shape, audit chain entry kinds, or error codes, this document binds. The `wcp/0.2` schema identifier on individual typed objects is preserved as the wire constant.

Companion normative documents updated alongside this spec: `spec/federation.md` (settlement-flavoured federation content removed), `spec/conformance.md` (Level 3 rewritten as pure federation), `spec/error-codes.md` (-44xxx removed, -47xxx added), `spec/threat-model.md` (settlement-specific threats removed), `spec/privacy-architecture.md` (settlement-specific privacy content removed). JSON schemas under `spec/schemas/` updated to match this document.

## 0. Statement of change from v0.95 to v0.955

v0.95 (and the v0.2 surface it inherited) anchored four primitives at the protocol layer: typed attestation, supervised handoff, two-phase settlement, and partial-completion abort. Operator feedback through the v0.7 and v0.85 cycles converged on the view that settlement is marketplace-specific: an escrow integration, a payout schedule, a dispute-mediation policy, and a refund mechanism are concerns that vary by deployment (consumer marketplace, corporate facility, research lab, mutual-aid network, defence logistics) and do not belong in the coordination protocol.

v0.955 reduces the protocol surface to coordination, attestation, and audit only. Value flow moves to a layer above WCP. Marketplaces, ERPs, grant systems, and inter-agency invoicing systems subscribe to WCP audit chain events (specifically `task_completed`, `task_voided`, `task_aborted`) as the trusted signal of work completion and run their own settlement logic against that signal. WCP does not move value, does not hold escrow, does not mediate disputes, and does not specify a settlement substrate.

Concretely, four things move out of WCP and one thing moves in:

- Out: `tasks/settle` RPC, the `settlement` block on the task descriptor, settlement-related audit chain entries, the `disputed` and `refunded` terminal states, the settlement error code range, and all federation content that concerned cross-coordinator value transfer.
- Out: the dispute mechanism. Disputes were a marketplace-layer concept that smuggled value-flow semantics into the protocol.
- Out: the override-authority pattern on the settlement block. Operators that need a manual override path build it in the settlement layer above.
- Out: the cross-coordinator settlement clearing RFC (`rfcs/0032-...`), withdrawn.
- In: a recheck mechanism on the existing `tasks/attest` call. When the verifier rejects evidence, the worker may re-attest up to `max_attestation_attempts` times before the task voids. This replaces the dispute-and-refund flow with a clean coordination-only retry semantics.

The four-pillar argument tightens to three pillars: irreversibility, attestation, and cross-organisational trust. Accounting is not a protocol concern.

## 1. The 8-RPC surface

v0.955 locks at eight RPCs. The set is:

```
capabilities/list
capabilities/subscribe
tasks/post
tasks/claim
tasks/execute
tasks/attest
tasks/supervise
tasks/abort
```

Dropped from the v0.95 set: `tasks/settle`. The implicit completion signal moves to the audit chain: when the verifier passes, the coordinator emits a `task_completed` entry. Settlement layers subscribe to that entry and trigger their own actions.

The semantics of the remaining eight RPCs are unchanged from `spec/0.2.md` Section 3, with the following narrow exceptions:

- `tasks/post` (Section 3.3): the request body's `task` MUST NOT contain a `settlement` block. Coordinators MUST reject posts that include the legacy `settlement` field with `INVALID_DESCRIPTOR` (error -42010, see Section 5). The `task` body MAY contain the new optional fields `max_attestation_attempts` and `accounting_ref` (Section 4).
- `tasks/attest` (Section 3.6): the response's `verifier_decision: "fail"` now branches based on the attempt counter on the coordinator side. If attempts remain, the task transitions to `rechecking` and the worker MAY resubmit with new evidence. If no attempts remain, the task transitions to `voided`. The attempt counter is coordinator-managed; the worker does not pass it.
- `tasks/abort` (Section 3.9): the `proposed_settlement` field is removed. The body shape becomes `{ claim_id, reason, state_snapshot }`. Coordinators MUST reject aborts that include the legacy `proposed_settlement` field with `INVALID_PARAMS` (-32602).

All other RPCs are byte-compatible at the wire envelope with the v0.95 surface.

## 2. State machine

The new canonical state machine:

```
                     tasks/post
            [start] -----------> ( posted )
                                    |
                                    | tasks/claim (accepted)
                                    v
                                ( claimed ) ----------+
                                    |                 |
                                    | tasks/execute   | tasks/abort
                                    v                 v
                +---------- ( executing ) ------> ( aborted )
                |              |  ^                   ^
 tasks/supervise|              |  |  tasks/abort      |
                v              |  | (executing path)  |
            ( supervising )----+  +-------------------+
                |              |
                | tasks/super  | tasks/attest
                | (releases)   v
                +---------> ( attesting )
                                 |       |       |
                verifier=pass    |       |       | verifier=fail
                                 |       |       |   AND attempts left
                                 v       |       v
                          ( completed )  |  ( rechecking )
                                         |       |
                                         |       | tasks/attest (retry)
                                         |       v
                                         | ( attesting ) ---+
                                         |                  |
                                         |                  | verifier=fail
                                         |                  |   AND no attempts left
                                         |                  v
                                         |             ( voided )
                                         |
                                         | verifier=fail
                                         | AND no attempts left
                                         v
                                    ( voided )
```

**States:** `posted`, `claimed`, `executing`, `supervising`, `attesting`, `rechecking`, `completed`, `voided`, `aborted`.

**Removed states** (relative to v0.95): `settled`, `disputed`, `refunded`.

**Terminal states:** `completed`, `voided`, `aborted`. The audit chain MUST contain exactly one terminal entry per task.

**Triggering RPCs on each edge:**

| From | To | RPC or trigger | Notes |
|---|---|---|---|
| (start) | posted | tasks/post | agent posts task; no escrow concept at the protocol layer |
| posted | claimed | tasks/claim | worker claims with `acceptance_attestation`; first-claim-wins with 100 ms tie-break grace |
| claimed | executing | tasks/execute | session opens; worker signs `execution_started` |
| claimed | aborted | tasks/abort | pre-execution; the protocol does not specify what happens to any external bond or marketplace reservation |
| executing | attesting | tasks/attest | worker submits attestations |
| executing | supervising | tasks/supervise | execution paused |
| supervising | executing | tasks/supervise | supervisor returns control to worker |
| executing | aborted | tasks/abort | mid-execution; the optional `state_snapshot` records partial progress for marketplace-layer settlement |
| attesting | completed | verifier=pass | terminal; audit entry `task_completed` |
| attesting | rechecking | verifier=fail AND attempts left | audit entry `recheck_requested` |
| rechecking | attesting | tasks/attest (retry) | worker re-attests with new evidence; coordinator increments attempt counter |
| attesting | voided | verifier=fail AND no attempts left | terminal; audit entry `task_voided` |

Every state transition emits a signed event into the hash-linked audit chain. The audit chain is shared substrate across worker classes; one code path, multiple worker classes.

## 3. Recheck mechanism

Recheck replaces the v0.95 dispute mechanism. It is a coordination-only retry: when the verifier rejects evidence, the worker is asked to re-attest with new or different evidence. After a configured number of attempts, the task voids. No money moves. No external resolver decides. No override authority adjudicates.

### 3.1 The `max_attestation_attempts` field

The task descriptor MAY include:

```json
"max_attestation_attempts": 1
```

- Type: positive integer.
- Default: `1`. Tasks with no `max_attestation_attempts` field behave as if `max_attestation_attempts: 1`.
- Operator policy: a coordinator MAY enforce a project-wide upper bound on this field via operator policy (e.g. reject posts requesting more than 5 attempts). The protocol does not specify the upper bound.
- Semantics: the worker may submit a maximum of `max_attestation_attempts` distinct `tasks/attest` calls per claim. The first call counts as attempt 1.

### 3.2 Behaviour

For each `tasks/attest` call against a claim:

1. The coordinator records the attempt by emitting an `attestation_attempt` audit entry with `{attempt_number, evidence_ref, collected_at}`. `attempt_number` starts at 1.
2. The verifier evaluates the submitted evidence against the task's `attestation_requirement`.
3. The verifier produces a decision: `pass`, `fail`, or `review`. The `review` outcome is unchanged from v0.95 semantics (operator-defined manual review path; out of scope at the protocol layer).
4. Routing:
   - `pass`: state -> `completed`. Audit entry `task_completed`. Terminal.
   - `fail` AND `attempt_number < max_attestation_attempts`: state -> `rechecking`. Audit entry `recheck_requested` with `{attempts_used, attempts_remaining}`. The worker MAY submit another `tasks/attest` call.
   - `fail` AND `attempt_number == max_attestation_attempts`: state -> `voided`. Audit entry `task_voided`. Terminal. Coordinator MUST return error code `RECHECK_MAX_ATTEMPTS_REACHED` (-47001) on any subsequent `tasks/attest` call against this claim.

The verifier MUST NOT branch on `attempt_number`. The verifier evaluates evidence the same way on every attempt. The attempt counter and the void-after-exhaustion are coordinator concerns, not verifier concerns. This separation preserves the spec's existing discrimination principle (verifier discriminates by `(mode, kind)`, never by attempt count, worker class, or settlement-layer state).

### 3.3 No new RPC

Recheck does not introduce a new RPC. It is a coordinator-side state-machine policy applied to the existing `tasks/attest` call. The worker SDK SHOULD surface `attempts_remaining` in the `tasks/attest` response so the worker can present a useful UI; the response shape becomes:

```
Response: { verifier_decision, residual?, reasons?, attempt_number, attempts_remaining }
```

The two new fields are additive; existing v0.95 SDKs that ignore them keep working at the wire level (they receive the standard `verifier_decision` and proceed).

### 3.4 Recheck and continuation_of

A task that voids does NOT automatically continue. The posting agent may post a new task with `continuation_of` referencing the voided claim, in which case the new task carries the original audit-chain linkage. The new task is independent at the lifecycle level; the verifier discriminates on the new evidence.

### 3.5 What recheck is not

Recheck is not a dispute mechanism. There is no third party adjudicating which evidence is "correct". There is only the verifier and the threshold rule the task descriptor specified at post time. If a worker and the verifier disagree, the worker re-tries with different evidence; if all attempts fail, the task voids and any settlement-layer system that depended on `task_completed` does not fire.

Recheck is not a backdoor for evidence that does not meet the requirement. The `attestation_requirement.threshold` (`any`, `all`, `M-of-N`) is unchanged. A worker that submits two pieces of evidence on attempt 1 and one piece on attempt 2 is evaluated independently on each attempt; cumulative evidence across attempts does not aggregate.

## 4. Descriptor schema changes

### 4.1 TaskDescriptor

Removed fields:

- `settlement` block in its entirety:
  - `currency`
  - `amount`
  - `escrow_provider`
  - `split` (with all entries)
  - `partial_completion_schedule`
- `attestation_requirement.override_authority`
- `attestation_requirement.override_audit_required`
- `attestation_requirement.override_allowed`

Added fields:

- `max_attestation_attempts` (positive integer, optional, default 1). See Section 3.
- `accounting_ref` (string, optional). Opaque to WCP. Used by external settlement layers to correlate WCP tasks with their own state. Examples of acceptable values: a Stripe `PaymentIntent` ID, an SAP cost-centre work-order number, a research-grant disbursement reference, a custom internal correlation token, or the empty string. WCP records the value verbatim in the audit chain `task_posted` entry and never inspects it.

The post-v0.955 TaskDescriptor shape:

```json
{
  "schema_version": "wcp/0.2",
  "task_id": "uuid",
  "posted_by": "did:wcp:<agent>",
  "descriptor_type": "transport | scheduled_presence | observe_and_report | <ext>",
  "descriptor_payload": { /* application-layer; opaque */ },

  "constraints": {
    "capabilities_required": { /* CapabilityDescriptor-shaped query */ },
    "time_window": { "earliest": "...", "latest": "..." },
    "location_scope": { /* venue+map or geohash polygon */ },
    "worker_class_filter": {
      "allowed": ["human", "autonomous_robot", "teleoperated_robot",
                  "semi_autonomous", "hybrid"]
    }
  },

  "attestation_requirement": {
    "modes": ["sensor-witness" | "third-party-witness" |
              "cryptographic-presence" | "owner-sign-off"],
    "threshold": "any" | "all" | "M-of-N",
    "M": 2,
    "N": 3,
    "evidence_schema": [
      { "mode": "sensor-witness",
        "kinds": ["gps_track", "indoor_pose_track", "weight_delta",
                  "photo_with_exif"] },
      { "mode": "third-party-witness",
        "kinds": ["customer_signature", "phone_app_attestation",
                  "iot_beacon_proximity"] }
    ]
  },

  "max_attestation_attempts": 3,
  "accounting_ref": "external-allocation-XYZ",

  "continuation_of": {
    "claim_id": "uuid-of-prior-claim",
    "required_evidence_kinds": ["..."]
  },

  "supervision": { "default": "autonomous", "escalation_policy": "..." },

  "x-subcontract-allowed": false
}
```

The `continuation_of` field added in v0.95 is unchanged in v0.955.

### 4.2 CapabilityDescriptor

No changes. The capability descriptor in `spec/0.2.md` Section 4 is preserved verbatim.

### 4.3 AttestationEvidence

No structural change. The verifier discrimination rule (`(mode, kind)`) is unchanged.

## 5. Audit chain entry kinds

Removed kinds (relative to v0.95):

- `escrow_capture`
- `escrow_release`
- `escrow_refund`
- `settlement_split`
- `federation_settlement_transfer`
- `override_resolution`
- `dispute_opened`
- `dispute_resolved`
- `refund_issued`

Added kinds:

- `task_completed`. Emitted on verifier `pass`. Carries `{claim_id, task_id, completed_at, accounting_ref}`. The `accounting_ref` is the opaque external reference from the original `tasks/post`; settlement layers subscribe to this entry and use the reference to drive their own actions.
- `task_voided`. Emitted on verifier `fail` when no attempts remain. Carries `{claim_id, task_id, voided_at, attempts_used, last_verifier_decision, accounting_ref}`.
- `attestation_attempt`. Emitted on every `tasks/attest` call before the verifier runs. Carries `{claim_id, attempt_number, evidence_ref, collected_at}`.
- `recheck_requested`. Emitted when the verifier fails and attempts remain. Carries `{claim_id, attempt_number_just_failed, attempts_remaining, verifier_reasons}`.

Preserved kinds (unchanged from v0.95):

- `task_posted`, `task_claimed`, `task_attest_submitted`, `verifier_decision`, `task_aborted`, `task_supervised`
- `federation_capability_advertised`, `federation_task_forwarded`, `federation_audit_chain_imported` and the other non-settlement federation entries (full list in `spec/federation.md`)

The hash-linked structure of the audit chain is unchanged: each entry carries the hash of the previous entry, signed by the coordinator.

## 6. Error codes

Removed range:

- `-44001` SETTLEMENT_FAILED
- `-44002` SETTLEMENT_DISPUTED
- `-44003` SETTLEMENT_REFUNDED
- (any other -44xxx error)

The -44xxx range is reserved and unused in v0.955. RFCs MAY repurpose it after v1.0 final via the standard deprecation process.

Added range:

- `-47001` RECHECK_MAX_ATTEMPTS_REACHED. Returned on `tasks/attest` when the claim is already in `voided` state because attempts were exhausted.
- `-47002` RECHECK_NOT_AVAILABLE_FOR_TASK. Returned on `tasks/attest` when the task explicitly disabled rechecks (e.g. `max_attestation_attempts: 0` if an operator policy allows that interpretation as "disable retry").

Additional descriptor-validation error:

- `-42010` INVALID_DESCRIPTOR. Returned on `tasks/post` when the descriptor contains a legacy `settlement` block, or a legacy `override_authority` / `override_audit_required` / `override_allowed` field. Migration error; intended to be a hard signal during the v0.95 -> v0.955 transition.

The summary block in `spec/error-codes.md` reflects these changes.

## 7. Migration guide: v0.95 -> v0.955

This section is the practical guide for adopters of v0.95 moving to v0.955. It enumerates the changes by adopter type.

### 7.1 Agent (caller side)

Required changes:

1. Stop sending the `settlement` block on `tasks/post`. The block is rejected with `INVALID_DESCRIPTOR` (-42010).
2. Stop sending the `proposed_settlement` field on `tasks/abort`. The field is rejected with `INVALID_PARAMS` (-32602).
3. Stop calling `tasks/settle`. The RPC does not exist. Calls return `METHOD_NOT_FOUND` (-32601).
4. Stop subscribing to settlement-related audit entries. Subscribe instead to `task_completed`, `task_voided`, and the existing `task_aborted` for terminal signal.

Recommended changes:

5. Set `accounting_ref` on each task to the correlation token your settlement layer uses (Stripe PaymentIntent ID, ERP work-order number, grant code, or empty string).
6. Set `max_attestation_attempts` based on the descriptor type and operator policy. For domains where verifier signal can be noisy (GPS dropout, sensor occlusion), 2 or 3 is reasonable. For domains where a single clean attestation is the expectation, leave at the default 1.
7. Implement a settlement layer on top of WCP that subscribes to the audit chain. The reference architecture is: a settlement service watches `task_completed` and `task_voided` events, looks up the `accounting_ref`, and triggers the settlement system's own flow (escrow capture, invoice issuance, grant disbursement, etc.).

### 7.2 Worker (callee side)

Required changes:

1. Stop expecting a `tasks/settle` callback after attestation. The protocol does not signal monetary settlement; that is the settlement layer's concern.
2. Handle the recheck loop: a `tasks/attest` response with `verifier_decision: "fail"` and `attempts_remaining > 0` means the worker can re-attest. The worker SDK SHOULD make this loop ergonomic.
3. Treat `verifier_decision: "fail"` with `attempts_remaining: 0` as terminal failure for this claim.

Recommended changes:

4. Provide a UX path for "collect new evidence and retry" when in the `rechecking` state. The user-facing copy should distinguish recheck (a coordination retry; you may be able to fix this) from void (terminal; you cannot fix this within this claim).

### 7.3 Coordinator implementer

Required changes:

1. Remove the `tasks/settle` handler.
2. Update the state machine to the v0.955 shape (Section 2).
3. Implement the attempt counter on the per-claim record. The counter increments on each `tasks/attest` call before verifier dispatch.
4. Drop settlement-related database columns. A reference migration is provided at `wcp_coordinator/migrations/v0.955.py` for the FastAPI reference coordinator.
5. Emit the new audit entry kinds (`task_completed`, `task_voided`, `attestation_attempt`, `recheck_requested`).
6. Stop emitting the removed audit entry kinds.
7. Add the new error codes; remove the -44xxx range and the `INVALID_DESCRIPTOR` (-42010) check on legacy settlement fields.

Migration of existing in-flight data is operator-discretion. The reference migration drops settlement columns destructively. Production coordinators with in-flight v0.95 tasks SHOULD let those tasks reach terminal state under the v0.95 surface before redeploying to v0.955, or run a parallel deployment per claim cohort.

### 7.4 Settlement / marketplace integrator

Required changes:

1. Move escrow, payout, dispute, refund, and override logic out of any WCP-conformant coordinator and into a layer that consumes the WCP audit chain.
2. Subscribe to `task_completed` and `task_voided` events as the trusted completion signal.
3. Use `accounting_ref` on each `task_posted` / `task_completed` / `task_voided` entry to correlate WCP tasks with the marketplace's own state.
4. The settlement layer chooses its own dispute mechanism, refund window, override authority, currency, escrow provider, and party-split policy. None of these are protocol concerns.

The cross-coordinator settlement clearing case previously specified in `rfcs/0032-...` is withdrawn at v0.955. Marketplaces that need cross-coordinator value transfer build that layer using audit chain subscriptions across both coordinators; WCP federation primitives (`spec/federation.md`) provide the coordination and audit interop substrate to do this above the protocol.

### 7.5 Conformance suite consumer

The conformance levels (`spec/conformance.md`) reorganise:

- **Level 1**: protocol surface tests now exercise 8 RPCs, not 9. Tests include `tasks/post` rejecting a legacy `settlement` block, and `tasks/post` accepting `max_attestation_attempts` and `accounting_ref`.
- **Level 2**: attestation correctness expands to include the recheck flow (success on attempt N, void after exhaustion). The verifier-discrimination-by-(mode,kind) tests are unchanged.
- **Level 3**: federation. The Level 3 suite is rewritten to remove all settlement-flavoured cases. Cross-coordinator coordination, capability discovery, audit chain interop, and cross-coordinator recheck (a voided task on coordinator A; the agent posts a continuation on the same coordinator; the continuation is claimable by a worker on coordinator B) are the new Level 3 surface.

Case counts are preserved: 4 Level 1, 13 Level 2, 10 Level 3.

## 8. What does NOT change

For the avoidance of doubt, the following are unchanged from v0.95:

- The four attestation modes: `sensor-witness`, `third-party-witness`, `cryptographic-presence`, `owner-sign-off`.
- The five worker classes: `human`, `autonomous_robot`, `teleoperated_robot`, `semi_autonomous`, `hybrid`.
- The four agent classes added in v0.95: `llm_agent`, `embodied_agent`, `scheduled_agent`, `human_supervisor`. Informational only; matching engine and verifier do not branch on agent class.
- The `continuation_of` block on task descriptors added in v0.95.
- The verifier's discrimination by `(mode, kind)`.
- The audit chain's hash-linked structure.
- The federation primitives for coordination and audit interop (`spec/federation.md` Sections covering capability discovery, task forwarding, audit chain import).
- The DID method `did:wcp` (`spec/did-method-wcp.md`).
- The wire-level JSON-RPC 2.0 over WebSocket transport.
- The TLS 1.3 baseline.
- The canonical-JSON signature scheme (RFC 8785).
- The reputation portability rules (reputation accrues to the worker DID).

## 9. Versioning note

v0.955 is a breaking-change codebase release. The `schema_version` wire constant on every typed object remains `wcp/0.2` because the typed object shapes either preserve their schema (capability descriptor, attestation evidence) or remove fields without renaming the envelope (task descriptor, audit chain entries). Adopters that key off the wire schema string for compatibility detection MUST also key off the absence/presence of the removed fields, the changed RPC set, and the changed audit entry kinds. A future v0.5 protocol identifier MAY ship to make the wire-level break unambiguous; v0.955 prioritises a minimal disruption to existing JSON-RPC envelopes for adopters partway through integration.

The TSC tracks two open questions for the next minor release: (a) whether to introduce a wire-level `wcp/1.0` identifier that retires `wcp/0.2`, and (b) whether to make `accounting_ref` mandatory or formalise its expected shape. Both are RFC-tracked.
