# Worker Context Protocol (WCP) v0.95

**Status:** release candidate. Additive over v0.85. No protocol surface change.
**Editors:** WCP TSC.
**License:** Apache 2.0.
**Compiled:** 2026-05-23.
**Schema version:** `wcp/0.2` (unchanged; rc5 is informational metadata only).

This document is a thin layer over `spec/0.2.md` and the additions cumulated through the v0.85 codebase release. It adds two informational fields that surface a pattern that was already mechanically supported but invisible in the public surface: an autonomous robot acting as a WCP agent and dispatching follow-up work to other workers, including other robots.

The protocol semantics, the nine RPCs, and the verifier discipline are unchanged. Coordinators MUST NOT branch on either field added in this document. Workers and operators MAY filter on them through the existing `class_extension` and runbook patterns.

---

## 1. Motivation

v0.2 defines five worker classes (`human`, `autonomous_robot`, `teleoperated_robot`, `semi_autonomous`, `hybrid`) and three roles bound to DIDs: worker, principal, agent. The agent role is described in terms of a coordinator-issued credential bound to "the AI-platform account". As production deployments of humanoid and mobile robots advance, a class of agents emerges that does not fit the "AI-platform account" framing: an autonomous robot's own onboard controller posting follow-up tasks to other workers from inside its execute loop. Worked examples include a humanoid robot completing a task and dispatching a place-on-shelf subtask to a stationary manipulator; an autonomous mobile robot finishing a transport leg and posting a load-handoff task to a forklift; an inspection drone completing a sweep and posting an anomaly-investigation task to a ground worker.

v0.85 mechanically supports this pattern: the agent role is a credential and any DID can hold one. v0.95 makes the pattern visible. Two additive fields land:

1. An `agent_class` declaration on the agent credential, parallel to `worker_class` on the capability descriptor.
2. A `continuation_of` block on the task descriptor that names the prior task whose attestation a follow-up posts against.

Both are informational. Neither changes verifier semantics. The forcing-function matrix (`spec/d4-verification-0.2.md`) holds; the same nine RPCs handle the new shape with no per-class branching.

## 2. `agent_class` enum on the agent credential

The agent credential (described in `spec/0.2.md` Section 7) carries the following new optional field:

```
agent_class: "llm_agent" | "embodied_agent" | "scheduled_agent" | "human_supervisor"
```

Semantics:

- **`llm_agent`** (default): a language-model-driven agent issuing tasks from a planner loop. Most v0.2 through v0.85 reference agents are this class.
- **`embodied_agent`**: an agent whose runtime is inside a physical worker. The agent's DID is bound to the worker's principal, but the credential exists independently of the worker credential. A humanoid robot posting follow-up tasks during its own execute loop is the canonical example.
- **`scheduled_agent`**: an agent driven by a fixed schedule rather than a planner. Periodic-inspection deployments and recurring-maintenance scheduling are typical.
- **`human_supervisor`**: an agent operated directly by a human via a console. Disaster-response incident commanders posting tasks to mixed teams are the canonical example.

The field is informational. Coordinators MUST NOT branch matching or attestation logic on `agent_class`. (Settlement was previously also listed here; settlement is removed from the protocol at v0.955 entirely, so the prohibition is moot at the protocol layer.) Workers MAY filter on it through `worker_class_filter.allowed_agent_classes` (a new optional sibling of the existing `allowed` field, identical in shape). Operators MAY use it for accounting, audit-log readability, and federation trust-anchor scope declarations.

The field MAY be absent. Absence means `llm_agent` for v0.95 compatibility. Future RFCs MAY register additional values via the standard process.

## 3. `continuation_of` task descriptor metadata

The task descriptor carries the following new optional block at the top level:

```json
{
  "continuation_of": {
    "claim_id": "<prior task's claim_id>",
    "required_evidence_kinds": ["<evidence kind>", "..."]
  }
}
```

Semantics:

- `claim_id` references a prior task whose attestation has completed (terminal `task_completed` audit entry). The follow-up task's runbook assumes the prior task's evidence is available for inspection.
- `required_evidence_kinds` lists the evidence kinds the follow-up task depends on. Operators MAY use this to verify that the prior task produced the expected evidence before claiming.

The verifier MAY read the block to surface continuation chains in the audit chain, but MUST NOT enforce continuation as a precondition for accepting `tasks/post`. The agent's runbook is the authoritative point of continuation policy.

The block is application-layer metadata. It records, in machine-readable form, what was previously left in `descriptor_payload` by convention. Existing deployments that use `descriptor_payload.x-continuation-of` (a known convention from v0.85 operator guides) MAY migrate to the structured field; both forms are accepted in v0.95 and the structured field is preferred.

## 4. Architectural invariants

- The eight RPCs from v0.955 are unchanged by this addendum. (At v0.95 / codebase tag v0.95 these were nine; v0.955 reduced them to eight by removing `tasks/settle`.)
- The forcing-function matrix passes unchanged. Adding the robot-as-agent case adds zero per-class branches to either the matching engine or the verifier.
- Settlement is out of scope at the protocol layer (since v0.955). A continuation task is independent of any settlement-layer correlation; both the prior and follow-up tasks emit their own `task_completed` / `task_voided` audit entries, and any settlement layer above WCP correlates via `marketplace_ref` independently.
- Federation is unchanged. A robot-as-agent on Coordinator A can post a continuation task to a worker on Coordinator B through the existing federation primitives without protocol modification.

---

## 5. Conformance

A v0.95-conformant implementation:

- Accepts the `agent_class` field on agent credentials and preserves it through registration and discovery.
- Accepts the `continuation_of` block on task descriptors and preserves it in the audit chain entry for the task.
- Does NOT branch matching or attestation logic on either field. (Settlement-layer branching is moot at the protocol layer since v0.955.)
- Passes the existing Level 1 / 2 / 3 conformance suites with the eight new cases added in v0.95 (three at Level 1 for robot-as-agent post/claim, three at Level 2 for `continuation_of` evidence chaining, two at Level 3 for cross-coordinator robot-as-agent).

## 6. Reference implementation

The reference coordinator and the four reference SDKs (Python, TypeScript, Rust, Go) ship a `RobotAgent` helper that wraps the post-from-inside-execute-loop pattern with the canonical signature `post_continuation(prior_claim_id, descriptor)`. The helper is convenience code; nothing about the wire protocol requires it.

A seventh reference agent, `examples/agents/delivery-robot-dispatcher/`, demonstrates the pattern end to end. An autonomous mobile robot inside a manufacturing facility claims a `transport` task, completes the move, attests, and then posts a `place_on_shelf` follow-up via `continuation_of` that a stationary manipulator (a different worker class) claims.

---

## 7. What v0.95 is not

- Not peer-to-peer task negotiation. Robot A posts through the coordinator; Robot B claims through the coordinator. The coordinator mediates as it does for any other task.
- Not swarm coordination. The robot-as-agent pattern is one task to one worker, repeated. Workers do not share state during execution.
- Not joint execution. Continuation is sequential: one task completes, the next is posted. No overlap, no shared `claim_id`.
- Not real-time. Continuation latency is bounded by `tasks/post` -> `tasks/claim` matching latency, which is the same as for any other task.
