# Worker Context Protocol (WCP) Specification v0.1

**Status:** draft, pre-publication
**License:** Apache 2.0
**Editors:** Rentably Pte Ltd (UEN 202612506Z)
**Date:** 2026-05-23

WCP is an open standard for AI agents to hire physical-world workers of any class (human contractor, autonomous robot, teleoperated robot, semi-autonomous system, hybrid) through one worker-agnostic RPC surface. WCP standardizes the contract for capability publish, task post, claim, execute, attest, settle, supervise, and abort. WCP does not standardize task semantics or worker bodies; those live in the application layer.

This document is normative. RFCs in `rfcs/` extend or amend this spec via the lazy-consensus process in `RFC_PROCESS.md`.

---

## 1. Settlement state machine (canonical)

```
                       tasks/post
              [start] -----------> ( posted )
                                      |
                                      | tasks/claim (accepted)
                                      v
                                  ( claimed ) ----------+
                                      |                 |
                                      | tasks/execute   | tasks/abort
                                      v                 v
                  +---------- ( executing ) ------> ( aborted )
                  |                |  ^                   ^
   tasks/supervise|                |  |  tasks/abort      |
                  v                |  | (executing path)  |
              ( supervising )------+  +-------------------+
                  |                |
                  | tasks/supervise|
                  | (supervisor    | tasks/attest
                  |  releases)     v
                  +-----------> ( attesting )
                                   |       |       |
                  verifier=pass    |       |       | verifier=fail
                  tasks/settle     |       |       |  or dispute opened
                                   v       |       v
                              ( settled )  |  ( disputed )
                                           |    |       |
                                           |    |       | dispute closes
                                           |    v       v
                                           | ( refunded ) <-- partial path
                                           +----------------> ( settled )
                                              partial via partial_completion_schedule
```

**States:** `posted, claimed, executing, supervising, attesting, settled, disputed, refunded, aborted`.

**Triggering RPCs on each edge:**

| From | To | RPC | Notes |
|---|---|---|---|
| (start) | posted | tasks/post | agent posts task with TaskDescriptor; bond held |
| posted | claimed | tasks/claim | worker claims with `acceptance_attestation` signed assertion; first-claim-wins with 100 ms tie-break grace |
| claimed | executing | tasks/execute | session opens; worker emits signed `execution_started` event |
| claimed | aborted | tasks/abort | pre-execution; bond refunded or partial forfeit per terms |
| executing | attesting | tasks/attest | worker submits attestations matching the requirement |
| executing | supervising | tasks/supervise | execution paused; settlement clock paused |
| supervising | executing | tasks/supervise | supervisor returns control to worker |
| executing | aborted | tasks/abort | mid-execution; `partial_completion_schedule` applies |
| attesting | settled | tasks/settle | verifier_decision=pass; release per split |
| attesting | disputed | (verifier) | verifier_decision=fail or party opens dispute within window |
| disputed | settled / refunded | (out-of-band) | dispute resolution closes |

Every state transition emits a signed event into a hash-linked audit chain. The audit chain is the shared substrate between the human-contractor production path and the robot path; one code path, two worker classes.

## 2. Transport

WCP uses JSON-RPC 2.0 over WebSocket for long-lived sessions and HTTPS plus webhooks for backends that cannot hold a connection. WebSocket is required because worker sessions are multi-message per task with mid-execution telemetry.

**MQTT rejection rationale.** MQTT (the VDA 5050 transport [reasoned]) was considered and rejected. The worker fleet is multi-tenant cross-operator from day one. An MQTT broker concentrates trust at the wrong layer under multi-tenancy: the broker either becomes a privileged third party (defeating decentralization) or a free-for-all (defeating attestation). JSON-RPC over WebSocket lets each coordinator be its own trust root, and multiple coordinators interop through worker DIDs without any broker mediation.

**Canonical JSON.** All signatures are computed over the canonical JSON serialization per RFC 8785 (JSON Canonicalization Scheme).

**JSON-RPC errors.** Errors return structured JSON-RPC error objects with codes from the enum in section 11.

## 3. The nine RPCs

### 3.1 capabilities/list (worker -> coordinator)

```
Request:
  {}

Response:
  {
    "worker_id": "did:wcp:<base58>",                       // R
    "capabilities": <CapabilityDescriptor>,                // R
    "ttl_seconds": 3600,                                   // R
    "revision": 42                                         // R, monotonic
  }
```

The coordinator MAY cache capabilities for `ttl_seconds` before requiring a refresh.

### 3.2 capabilities/subscribe (agent -> coordinator)

```
Request:
  {
    "filter": <CapabilityQuery>,                           // O
    "since_revision": 41                                   // O
  }

Response (one-shot):
  {
    "subscription_id": "uuid",                             // R
    "stream_endpoint": "wss://.../sub/<subscription_id>",  // R
    "ttl_seconds": 3600                                    // R
  }

Followed by stream messages over `stream_endpoint`:
  {
    "worker_id": "did:wcp:...",
    "capabilities": <CapabilityDescriptor>,
    "revision": 43
  }
```

### 3.3 tasks/post (agent -> coordinator)

```
Request:
  {
    "task": <TaskDescriptor>,                              // R
    "bond_ref": "stripe:pi_...",                           // R, reference to held escrow
    "expiry": "2026-06-01T18:00:00Z",                      // R
    "supervision": <SupervisionRequirement>                // O
  }

Response:
  {
    "task_id": "uuid",                                     // R
    "eligible_workers_count": 7,                           // R, post-filter
    "posted_at": "ISO-8601"                                // R
  }
```

The coordinator pre-validates `task.attestation_requirement` against the schema registry (RFC 0003). Posts with `M > N` or unsupported modes fail with error code `INVALID_ATTESTATION_REQUIREMENT`.

### 3.4 tasks/claim (worker -> coordinator)

```
Request:
  {
    "task_id": "uuid",                                     // R
    "worker_id": "did:wcp:...",                            // R
    "bid": "12.50",                                        // O
    "eta": "2026-06-01T14:30:00Z",                         // R
    "acceptance_attestation": {                            // R
      "sig": "...",                                        // R, Ed25519 signature
      "alg": "Ed25519",                                    // R
      "payload_hash": "...",                               // R, canonical-JSON hash of
                                                           //    {task_id, accepted_terms,
                                                           //     worker_pubkey, eta}
      "signed_at": "ISO-8601"                              // R
    }
  }

Response:
  {
    "claim_id": "uuid",                                    // R
    "accepted": true,                                      // R
    "counter": <Terms>,                                    // O, if counter-offered
    "reason": null                                         // O, e.g. "preempted"
  }
```

**The `acceptance_attestation` field is the worker's explicit signed acceptance.** A claim without a valid signature is rejected. The audit chain records the signature so neither party can later deny consent. Lever: informational (uncertainty about worker assent eliminated by typed signature).

**Race semantics (Scenario 4).** tasks/claim is serialized by the coordinator. First-claim-wins with a 100 ms grace window during which late claims may tie-break by `bid` (lowest bid wins). Losers receive `accepted=false, reason="preempted"`.

### 3.5 tasks/execute (bidirectional after open)

```
Request:
  {
    "claim_id": "uuid"                                     // R
  }

Response (server-side stream):
  {
    "event_type": "execution_started" |
                  "picked_up" |
                  "arrived_at_dropoff" |
                  "checkpoint" |
                  "heartbeat" |
                  "supervision_tier_changed" |
                  "<application-defined>",                 // R
    "timestamp": "ISO-8601",                               // R
    "payload": { ... },                                    // R, opaque to RPC
    "sig": "..."                                           // R, worker signature over event
  }
```

**Heartbeat (Scenario 5).** The worker MUST emit a `heartbeat` event every 15 seconds during `executing` state. Three missed heartbeats (45 seconds) trigger an automatic transition to `supervising` with `handoff_reason="connectivity_lost"`. If the worker reconnects with a signed `state_snapshot` within the supervision window, execution resumes; otherwise tasks/abort fires with `reason="worker_lost"` and `partial_completion_schedule` applies.

### 3.6 tasks/attest (worker -> coordinator)

```
Request:
  {
    "claim_id": "uuid",                                    // R
    "attestations": [<AttestationEvidence>, ...],          // R
    "compensating_action": { ... }                         // O, if partial
  }

Response:
  {
    "verifier_decision": "pass" | "fail" | "review",       // R
    "residual": { ... },                                   // O, evidence gaps
    "reasons": ["...", "..."]                              // O, when fail or review
  }
```

The verifier evaluates each `AttestationEvidence` against the task's `attestation_requirement.evidence_schema` and applies the threshold (`any | all | M-of-N` with explicit M and N).

### 3.7 tasks/settle (coordinator -> settlement layer)

```
Request:
  {
    "claim_id": "uuid",                                    // R
    "decision": "release" | "refund" | "partial",          // R
    "amount": "12.50",                                     // R
    "party_breakdown": [
      {"party": "did:wcp:<worker-principal>", "amount": "10.00"},
      {"party": "did:wcp:<platform>",         "amount": "1.875"},
      {"party": "did:wcp:<insurance-pool>",   "amount": "0.625"}
    ]
  }

Response:
  {
    "settlement_id": "uuid",                               // R
    "state": "captured" | "refunded" | "partial",          // R
    "receipt_url": "https://..."                           // O
  }
```

### 3.8 tasks/supervise (worker -> coordinator, or coordinator -> human pool)

```
Request:
  {
    "claim_id": "uuid",                                    // R
    "handoff_reason": "uncertainty" |
                      "connectivity_lost" |
                      "safety_concern" |
                      "policy_required" |
                      "<application-defined>",             // R
    "state_snapshot": { ... },                             // R, signed worker state
    "urgency": "low" | "high" | "critical"                 // R
  }

Response:
  {
    "supervisor_id": "did:wcp:...",                        // R
    "session_url": "wss://.../sup/<session>",              // R
    "takeover_authority": "advise" | "co_pilot" | "full"   // R
  }
```

**The agent's contract does not move under the worker's feet.** If a worker upgrades or downgrades autonomy mid-task (Scenario 12), `supervision_tier_changed` is emitted as an `execute` stream event, but the `attestation_requirement` on the original `tasks/post` remains binding. If the worker can no longer satisfy the original requirement, the only paths out are tasks/supervise or tasks/abort.

### 3.9 tasks/abort (any party -> coordinator)

```
Request:
  {
    "claim_id": "uuid",                                    // R
    "reason": "worker_lost" |
              "worker_initiated" |
              "agent_initiated" |
              "principal_initiated" |
              "policy_violation" |
              "<application-defined>",                     // R
    "state_snapshot": { ... },                             // R
    "proposed_settlement": "split" | "refund" | "dispute"  // R
  }

Response:
  {
    "abort_id": "uuid",                                    // R
    "settlement_disposition": "applied" | "disputed"       // R
  }
```

## 4. CapabilityDescriptor

A capability descriptor is **worker-agnostic in its required block** and **opaque in its class_extension block**. The matching engine at v0.1 reads only the required block; the class_extension carries body-specific shape for application-layer filters.

```json
{
  "schema_version": "wcp/0.1",
  "worker_id": "did:wcp:<base58>",
  "principal_id": "did:wcp:<base58>",
  "class": "human | autonomous_robot | teleoperated_robot | semi_autonomous | hybrid",

  "required": {
    "current_location": { "geohash": "..." }
                      | { "venue_id": "...", "map_id": "..." },
    "available_windows": [
      { "rrule": "FREQ=DAILY;BYHOUR=8-22",
        "timezone": "Asia/Singapore" }
    ],
    "attestation_methods_supported": [
      "sensor-witness", "third-party-witness",
      "cryptographic-presence", "owner-sign-off"
    ],
    "certifications": [
      { "issuer": "BCA", "id": "...", "expires": "2027-03-01" }
    ],
    "policy_windows": [
      { "type": "geographic", "scope": "Singapore" }
    ],
    "attestation_keys": [
      { "kty": "OKP", "crv": "Ed25519", "x": "<base64url>" }
    ],
    "as_of": "ISO-8601"
  },

  "class_extension": {
    // OPAQUE to RPC layer. Examples (not exhaustive):

    // human worker
    "skills": ["aircon_servicing_quarterly", "fire_safety_inspection"],
    "languages": ["en", "zh", "ms"],
    "tools_carried": ["multimeter", "drain_snake_5m"],

    // autonomous robot
    "kinematics": { "locomotion": "wheeled", "max_speed_mps": 1.4,
                    "footprint_m": [0.6, 0.4] },
    "payload": { "max_kg": 5, "max_dim_m": [0.4, 0.4, 0.3] },
    "end_effectors": [
      { "class": "tray", "rated_for": ["solid_under_5kg"] }
    ],
    "environment": { "indoor": true, "ip_rating": "IP54",
                     "operating_temp_c": [5, 40] },

    // teleoperated / semi-autonomous additional
    "supervision_tier": {
      "default": "remote_human_per_session",
      "fallback": "autonomous_with_geofence",
      "operator_pool_id": "..."
    }
  }
}
```

Every typed object carries `schema_version`. The `attestation_keys` array uses JWK encoding per RFC 7517 [verified]. The `as_of` timestamp lets consumers reason about staleness.

## 5. TaskDescriptor with typed attestation requirement

```json
{
  "schema_version": "wcp/0.1",
  "task_id": "uuid",
  "posted_by": "did:wcp:<agent>",
  "descriptor_type": "transport | scheduled_presence | observe_and_report | <ext>",
  "descriptor_payload": { /* application-layer; opaque to RPC layer */ },

  "constraints": {
    "capabilities_required": { /* CapabilityDescriptor-shaped query */ },
    "time_window": { "earliest": "...", "latest": "..." },
    "location_scope": { /* venue+map or geohash polygon */ },
    "worker_class_filter": {
      "allowed": ["human", "autonomous_robot", "teleoperated_robot",
                  "semi_autonomous", "hybrid"]
    }
  },

  "attestation_requirement": {
    "modes": ["sensor-witness" | "third-party-witness" |
              "cryptographic-presence" | "owner-sign-off"],
    "threshold": "any | all | M-of-N",
    "M": 2,
    "N": 3,
    "evidence_schema": [
      { "mode": "sensor-witness",
        "kinds": ["gps_track", "indoor_pose_track",
                  "weight_delta", "photo_with_exif"] },
      { "mode": "third-party-witness",
        "kinds": ["customer_signature", "phone_app_attestation",
                  "iot_beacon_proximity"] }
    ],
    "override_allowed": true,
    "override_authority": "did:wcp:<operator-ops-role>",
    "override_audit_required": true
  },

  "settlement": {
    "currency": "SGD",
    "amount": "12.50",
    "escrow_provider": "stripe-rentably",
    "split": [
      { "party": "did:wcp:<worker-principal>", "pct": 80 },
      { "party": "did:wcp:<platform>",         "pct": 15 },
      { "party": "did:wcp:<insurance-pool>",   "pct": 5  }
    ],
    "partial_completion_schedule": [
      { "milestone": "...", "release_pct": 50 }
    ]
  },

  "supervision": {
    "default": "autonomous",
    "escalation_policy": "..."
  },

  "x-subcontract-allowed": false
}
```

Notes locked at v0.1:

- `evidence_schema` is **inline** as a typed array of `{mode, kinds}`. It is not a URI reference. The schema registry of allowed kinds lives in RFC 0003 and may grow by RFC without spec changes here.
- `override_authority` is typed as a DID, not a string array. The override path is a real signed action by a named identity.
- The settlement split example includes a named `insurance_pool` DID at 5%. The pool is not WCP-normative; the example reflects the human-side pilot.
- `x-subcontract-allowed` is a reserved extension field, default `false`. v0.1 forbids subcontracting at the worker layer (Scenario 13). Agents needing multi-worker workflows MUST compose multiple tasks at the agent layer. v0.2 will revisit via RFC 0002.

Lever: informational. Same lever as Spanner TrueTime [verified] (uncertainty typed into the call signature, applied to task completion proof).

## 6. AttestationEvidence

```json
{
  "schema_version": "wcp/0.1",
  "mode": "sensor-witness | third-party-witness | cryptographic-presence | owner-sign-off",
  "kind": "gps_track | indoor_pose_track | photo_with_exif | customer_signature | ...",
  "payload": { /* mode+kind-specific; see RFC 0003 */ },
  "payload_hash": "<sha256>",
  "sig": "<Ed25519 signature over canonical-JSON of {mode,kind,payload_hash,worker_id,claim_id,collected_at}>",
  "worker_id": "did:wcp:...",
  "claim_id": "uuid",
  "collected_at": "ISO-8601"
}
```

The verifier discriminates by `(mode, kind)`, never by worker class. This is the load-bearing point at which WCP enforces worker-class agnosticism in code.

## 7. Identity model

WCP uses W3C DID Core [verified, W3C Recommendation]. A new method `did:wcp` is registered in `spec/did-method-wcp.md`.

Three DIDs:

- **worker**: bound to a hardware-rooted keypair (TPM or secure element) where available; software keypair otherwise with declared trust class.
- **principal**: employer for humans; owner for robots; operator for teleoperated systems. Bound to a coordinator-verified account.
- **agent**: coordinator-issued credential bound to the AI-platform account.

### 7.1 Reputation portability

**Reputation accrues to the worker DID, not the principal DID.** On principal change (a robot is sold; a contractor changes employer), the worker DID's reputation pointer is inherited. Key history is maintained in the DID document; the worker may rotate keys while preserving the DID.

**Cross-class portability is single-DID by design.** A contractor who later supervises a robot retains one DID and accumulates a unified reputation across modes of work. This is intentional and load-bearing.

Structural cousin: same lever as GSMA eUICC remote SIM provisioning (informational and organizational, applied to physical-world workers across classes) [reasoned]. The eUICC analogy is the justification for the portability rule: identity moves with the worker, not the operator. Without this rule, a worker who switches employers loses all reputation, and a robot sold secondhand reads as fresh on day one, both of which break the marketplace's ability to learn from history.

## 8. D4 forcing function summary

Three descriptors x two worker classes = six cells. Each cell uses the nine RPCs unchanged. Full proof in `spec/d4-verification.md`.

| | robot | human |
|---|---|---|
| transport | AMR delivers toolbox; sensor-witness + third-party-witness, 2-of-2 | contractor walks smoke detector; gps_track + signature, 2-of-2 |
| scheduled_presence | cleaning robot in lobby; cryptographic-presence + sensor-witness, 2-of-2 | aircon quarterly service; cryptographic-presence + owner-sign-off, 2-of-2 |
| observe_and_report | drone CO2 sweep; sensor-witness 1-of-1 | fire-safety inspector; photo-bundle 1-of-1 |

All six cells pass with no RPC modification. Variance lives in `attestation_requirement.evidence_schema` and opaque `descriptor_payload`.

## 9. Competitive landscape and prior art

### 9.1 Robot side

- **VDA 5050** [reasoned]: open AGV/AMR fleet protocol over MQTT for one operator inside one facility. Does not cover marketplace posting, settlement, cross-operator identity, attestation, or supervision handoff. WCP justified by four missing slots; v0.2 ships a WCP-to-VDA-5050 reference adapter so AGV-fleet operators can bridge.
- **ROS 2 actions and services** [verified]: intra-robot or intra-fleet RPC; not a marketplace layer. WCP sits above; reference plugin uses ROS 2 actions internally to drive Nav2 and lifecycle nodes.
- **NVIDIA Isaac and Isaac ROS bridge** [reasoned]: simulation and accelerated perception stack. Adjacent, not competing. v0.2 will publish an Isaac Sim scene.
- **OPC UA Robotics Companion Spec** [reasoned]: industrial automation; over-engineered surface area; would break the 30-page budget by an order of magnitude.

### 9.2 Human side

- **TaskRabbit, Upwork, Fiverr, Toptal** [reasoned]: closed two-sided platforms with proprietary task and matching APIs. WCP is the open counter-move; these are demand we want to reach, not specs to extend.
- **Field service management protocols (ServiceTitan, Jobber, BlueFolder)** [reasoned]: internal back-office tools, not cross-platform agent dispatch. v0.2 will publish an outbound adapter so service businesses can sit on the WCP supply side without ripping out FSM.
- **Mercor and Pareto** [reasoned]: AI-talent matchmaking, not physical-world worker dispatch. Adjacent on the agent side only.

### 9.3 Cross-cutting

- **MCP** [verified at concept]: same lever as WCP (informational and algorithmic; in-band capability discovery plus typed call contract). **WCP cannot live as MCP extensions because MCP's invariants assume side-effect-free or trivially reversible tool calls; physical workers can drop payloads halfway.** MCP has no `attest`, `supervise`, `settle`, or partial-completion semantics; adding them inverts MCP's design center.
- **Matter / Project CHIP** [reasoned]: governance lesson, not technical overlap. The lesson is to pick a steward early and not stand up a consortium from scratch.
- **OCI image and runtime split** [verified]: governance template. WCP-the-spec and WCP-the-reference-plugins govern under this split.

### 9.4 FIPA-ACL and KQML (the "but this was tried in the 1990s" objection)

KQML (Knowledge Query and Manipulation Language, early 1990s, DARPA Knowledge Sharing Effort, Tim Finin at UMBC and Jay Weber at EITech [verified]) and FIPA-ACL (FIPA Agent Communication Language, late 1990s through 2000s, IEEE-backed FIPA consortium, 20-plus performatives including `inform`, `request`, `propose`, `accept-proposal`, JADE as the reference implementation [verified]) are the precedent multi-agent communication protocols WCP must answer for. Both are dead in production [verified, "adoption waned as the web exploded, and agents gave way to service-oriented architectures"].

Failure modes:

1. **Over-formal speech-act semantics.** 20-plus performatives imposed high cognitive load without a corresponding payoff in correctness.
2. **Ontology layer.** Assumed shared semantic ontologies would emerge across vendors. They did not.
3. **No settlement substrate.** No attestation layer. No production deployment incentive outside academic and e-commerce prototypes.
4. **The web ate the use case.** Service-oriented architectures and REST APIs absorbed the inter-system communication need with vastly lower ceremony.

WCP differs structurally on each axis:

1. **Typed RPC contract instead of speech-acts.** Nine named methods, not 20-plus performatives. The vocabulary is small enough to memorize.
2. **No shared ontology required.** The application-layer `descriptor_payload` is opaque to the RPC layer; the worker-class extension block is opt-in. Semantic agreement is bilateral between agent and worker, not a global precondition.
3. **Settlement is a first-class slot.** Wired to Stripe two-phase escrow from publication day. Attestation is typed into the task signature. Neither was true for FIPA-ACL.
4. **Production deployment is a launch precondition, not a research aspiration.** WCP runs in the Rentably wedge against real human-contractor jobs from Day 7.

Sources: [Wikipedia: KQML](https://en.wikipedia.org/wiki/Knowledge_Query_and_Manipulation_Language), [Wikipedia: Agent Communications Language](https://en.wikipedia.org/wiki/Agent_Communications_Language).

## 10. Out of scope at v0.1

The protocol mechanically supports any task class, but the v0.1 reference coordinator refuses to post tasks tagged for the following until explicit RFC-process clearance:

- Medical tasks (administering medication, clinical examinations, diagnostic procedures).
- Defense and military applications.
- Tasks involving minors as subjects.
- Hazardous-materials handling above consumer thresholds.

Subcontracting at the worker layer is also out of scope at v0.1 (Scenario 13). The `x-subcontract-allowed` field is reserved for v0.2; behavior under it is undefined and operator-discretionary at v0.1.

Humanoid manipulation, swarm coordination, and multi-step planning are out of scope for v0.1 reference implementations. The protocol does not prohibit them; the reference implementations do not implement them.

## 12. Conformance

A WCP-conformant implementation MUST:

1. Implement all 9 RPCs with the request/response shapes in Section 3.
2. Verify worker signatures on tasks/claim (`acceptance_attestation`), tasks/execute events, and tasks/attest evidence before mutating state.
3. Validate `attestation_requirement` against the schema registry (RFC 0003) before posting.
4. Emit signed, hash-linked audit chain entries on every state transition.
5. Honor the 15-second heartbeat with three-missed-heartbeats supervising transition.
6. Honor the 100 ms claim tie-break grace.
7. Honor the 72-hour `dispute_window` default unless the TaskDescriptor specifies otherwise.

A WCP-conformant implementation MAY:

1. Support additional `descriptor_type` values beyond the three published examples.
2. Support additional `class_extension` keys.
3. Implement `x-subcontract-allowed=true` behavior (non-conformant at v0.1; operator-discretionary).
4. Integrate alternative escrow providers in place of Stripe.
